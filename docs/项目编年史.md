## 2026-10 网页版首发：几个需要留下来的判断

### 版本号为什么是两套、tag 为什么只有一套

网页版用 `2.x.y`、桌面版用 `1.x.y`，**刻意不同号**，这样一眼能看出网页版是不是落后了
（网页版 `v2.0.0` 对应桌面版 `v1.3.5`）。但 **git tag 只保留桌面版这一套**：

- `release.yml` 在 `v*` tag 上断言 `python src/cli.py --version == tag`，而它取的是 `core.tag`。
  推一个 `v2.0.0` 会在这一步直接 throw —— 也就是说"网页版单独打 tag"在这个仓库里根本走不通，
  除非再开一套 `web-v*` 的流水线。一个仓库挂两套 tag 比混号更容易让人迷路，所以没有那么做。
- 因此 `core.tag` 提到了 v1.3.5（**纯粹为了让发布流程能跑**），网页版的 `2.x.y` 写在 Release 说明里。

### v1.3.5 的桌面版一个数字都没动

两版可互换比较结果。这一点是有断言兜着的：`web/src/core.js` 里的 `EXE_TAG` 必须等于 `core.tag`
（`tests/test_web_parity.py::test_web_core_declares_the_exe_version_it_ports`），
页内 351 项黄金向量由 `scripts/export_vectors.py` 从真的 `core.py` 重新生成并在 CI 里校验没过期。

### 一个已死控件暴露出的验证盲区

网页版的强调色取色器自上线起就是**完全点不动**的：回调里读了一个不存在的变量（`g`，实际
声明的是 `g2`），`'use strict'` 下每次拖动抛 `ReferenceError`。而当时 `tests/test_web_e2e.py`
里没有任何一条用例碰过这个控件，且那条文件在**所有**流水线上都是 skip（CI 不装 playwright）。
于是"数值对拍全绿 + 构建新鲜度全绿 + e2e 全绿（其实是 skip）"与"一整块可见功能是死的"同时成立。

处置：修掉它，并把 e2e 搬进 CI（`web-e2e` job，装 Playwright + Chromium）。**看到 skip 就是流水线坏了。**

### core 对拍看不见的那一层

`tests/test_web_parity.py` 比的是 `core.js ↔ core.py`。但用户看到的数字还要经过**单位换算**与
**批量规则**，它们分别在 `main.py`/`src/batch.py` 与 `web/src/ui.js` 里**各写了一遍**，而两边之间
此前没有任何自动检查。2026-10 的第三方复核正是从这一层找出三处不一（批量导出数值截到 4 位小数、
丢掉 A/B/C 之外的列、`#VALUE!` 写成文本），核心里一处都没有。新增的
`tests/test_web_ui_parity.py` 用源码扫描把两边对上，并断言「关于」页仍然逐条列出这些有意差异。

### 构建产物入库的唯一例外

`web/index.html` 是构建产物，却**入库**了 —— 因为网页版的交付形态就是一个 `.html`，
不入库就失去"在 GitHub 上点开即用"的价值。代价用三道闸兜住（`-text` 属性、构建新鲜度断言、
随发行资产上传），理由写在 `.gitignore` 与 `.gitattributes` 的注释里。

其中 `-text` 那条**最初的写法是错的，已更正**：当时断言"Windows 检出转成 CRLF 会让
`build_web.py --check` 失败、整套测试变红"。实测不成立 —— `--check` 用 Python 文本模式
`open()` 读文件，默认 `newline=None` 会开启 universal newlines，CRLF 被还原成 LF 再比较，
照样通过。错的根源是"在内存里把构建结果 replace 成 CRLF 再比字符串"，跳过了文件读取这一步。
它仍然值得加，但理由是另一个：让**交付物的字节不随检出平台变**，`dist/` 里那份 html 与
`SHA256SUMS.txt` 才有可比性。（这条更正本身也记在这里，因为"根因记述是错的"正是本仓库
v1.3.1 已经犯过一次的毛病。）

## 2026-10 出处复核：对 v1.3.1 / v1.3.2 记述的更正

v1.3.1 与 v1.3.2 都是在**未取得原始文献**的情况下下的根因结论。后续取得了那条中文文献的
原文页面位图并逐字核对，结论如下（只更正记述，**数值结果不变**）：

- **`Gili-水面` 的真名是「纪利公式」**，不是"吉利公式"（同音字抄错）。它属给排水/冷却塔工程，
  GB/T 50392-2016 第 5.1 节亦采用。旧文档"气象学文献中查无此式"的悬案由此解释：**检索用错了名字**。
- **索引来源**：周西华, 梁茵, 王小毛, 周令昌.《饱和水蒸汽分压力经验公式的比较》.
  辽宁工程技术大学学报, 2007, 26(3): 331–333.（文章编号 1008-0562(2007)03-0331-03）公式 (7)。
  该文列 7 条公式，与本站 6 条同名/同式；旧文档称其"与代码里 14 条公式无对应关系"**是错的**。
- **v1.3.1 改错了对象**：该式真正的问题是指数常数被抄成原文的 1/10
  （`0.00141966` vs 原文 `0.0141966`），使该式全区间恒定偏低 −2.90%（当年记为 −3.0%）。
  旧记述说"前因子 980.66 是错的、应为 1013.25"属误判 —— **980.66 hPa 就是原文的 98066 Pa，本来就对**。
  v1.3.1 把正确的前因子改掉、留下了错误的常数，反而让该式在自己的参考点上给出 1016.57 hPa（自相矛盾）；
  v1.3.2 删掉常数项后才真正校准。
- **参考温度 373.15 K 是有意偏离原文**（原文为 373.16 K）。373.16 K 是旧温标蒸汽点，
  与现代温标 `Tk = t + 273.15` 混用反而更差（实测对照 IAPWS-95：0.142% vs 0.178%）。
  原则是"数值以实现 + 外部真值为准，出处差异照实标注"。
- **`Gili-水面` 注册域 20 ℃ 上界放宽到 120 ℃**（下界仍 −10 ℃），与原文结论（0~120 ℃）一致；
  全域实测最大偏差 0.158%，远在 0.25% 容差内。
  这是 v1.3.4 唯一的行为变更，且**纯属新增**：全温度扫描（−20~120 ℃）下 0 处失去可用性、
  858 处新增，0 处数值变化；45 ℃ 时可用公式数由 8 条变为 9 条。
- **`Gili-水面` 下界取 −10 ℃，未跟随 GB/T 50392-2016 的"0 ℃ 以下不合理"**：那句话是国标基于
  **冷却塔工况**（湿空气比焓/含湿量链条、塔内结冰）说的，**不是水汽压精度上的退化**。实测冷端
  −10 ℃ 对 IAPWS-95 / Murphy & Koop 2005 为 −0.142% / −0.114%，与 +50 ℃ 同量级。
