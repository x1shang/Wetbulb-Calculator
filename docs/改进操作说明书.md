## 2. 有两处我**没有**照抄审计建议（请你过目）

审计是"外部视角的意见"，不是规范。下面两处我按你仓库的实际情况改了做法，理由都经过实测：

**① "二分反算要带 `tmin/tmax`（按公式声明域截断）" —— 照做会让日常输入直接报错。**

实测：`Buck-水面` 声明适用域是 0~80 ℃。在 **0 ℃、RH=60%** 这种每天都会遇到的输入下，
露点是 **−6.06 ℃**，落在声明域之外。若按公式声明域截断二分，这个输入会直接报错。
反算天生要略微越出"直接计算"的适用域，所以我的做法是：

- 二分仍在**工具全域 [−150, 200]** 内进行（与旧版一致，不改变正常行为）；
- 但补上真正的病态输入护栏：`e` 小到全域下界都达不到时**明确抛 `InputError`**，
  而不是像旧版那样把二分下界 **−150 ℃ 当成"露点温度"正常返回**（审计的 RH=0 探针就是这么来的）。

**② 附带发现：审计说的"Goff2 低温系数错"，不是系数整体错，而是第 4 个系数差 100 倍。**
`1.3816e-5` 应为 `1.3816e-7`（Goff-Gratch 1946 水面式）。改一个数字，0 ℃ 从 −3.48% 变 −0.09%。
另外那 8 个系数（A=373.15、B=7.90298、C=−5.02808、E=−11.344、F=0.0081328、
G=3.49149、H=lg(1013.246)=3.0057149）经逐项比对**都是对的**，没动。

> 还有一处需要你知道的边界：Gili 的**原始文献我没能取得**（审计也说了它在知网付费）。
> "980.66 应为 1013.25"的依据是两条自洽性论证，不是原文：
> (a) 该式参考点 373.16 K 是水沸点，那里饱和水汽压按定义 = 1 atm = 1013.25 hPa；
> (b) 替换后与公开参考表的残差从 −3.0% 降到 ≤0.28%。
> 这两条写在 `core.py` 的注释里了。**如果你能拿到原文，请核对一遍。**

### ⑦ 30 分钟 ·（可选）让 `Arden-水面` 在高温端真正可用

**问题**：`Arden-水面` 的系数 `(6.1121, 18.678, 257.14)` 是 Buck (1996) 的**三参数**式
`e_s = 6.1121·exp[(18.678 − T/234.5)·T/(257.14 + T)]`，
但 `magnus` 族只能表达两参数式 `A·exp(B·T/(C+T))`，于是 `−T/234.5` 修正项被丢掉了。
后果：25 ℃ 偏 +1.0%、30 ℃ +1.4%、40 ℃ +2.3%、50 ℃ +3.6%、**100 ℃ +12.7%**。

**我实算过的修法**（新增一个三参数族）——改完之后它在 0~100 ℃ 全段都 ≤0.08%：

```python
# src/core.py：加进 _FAMILY_TABLE 之前的两个函数
def _esat_buck96(T, coeff):
    """Buck(1996) 水面三参数式：e = A·exp[(B − T/D)·T/(C + T)]"""
    A, B, C, D = coeff            # (6.1121, 18.678, 257.14, 234.5)
    return A * math.exp((B - T / D) * T / (C + T))

def _dedt_buck96(T, coeff):
    A, B, C, D = coeff
    u = (B - T / D) * T / (C + T)
    du = -T / (D * (C + T)) + (B - T / D) * C / (C + T) ** 2
    return _esat_buck96(T, coeff) * du

_FAMILY_TABLE['buck96'] = dict(esat=_esat_buck96, dedt=_dedt_buck96)   # 无解析反算 → 自动走二分
```

然后把注册行改成：

```python
register_formula('Arden-水面', 'buck96', (6.1121, 18.678, 257.14, 234.5), -30, 50)
```

| 10 ℃ | +0.21% | +0.05% |
| 20 ℃ | +0.60% | −0.02% |
| 25 ℃ | +0.99% | +0.05% |
| 50 ℃ | +3.61% | +0.08% |

#### 顺带修掉一个大 bug：中文路径下程序根本打不开

这是整理过程中撞上的，**与整理本身无关，是原有缺陷**：

```
qt.qpa.plugin: Could not find the Qt platform plugin "windows" in ""
This application failed to start because no Qt platform plugin could be initialized.
（退出码 0xC0000409，窗口一闪即退）
```

**根因**：PySide2 把自己的包目录交给 Qt 时要经过一次窄字符（ANSI）转换，非 ASCII 路径被写成 `???`：

```
QLibraryInfo.location(PluginsPath)
  -> 'D:/desktop/projpy/???/.venv-build/lib/site-packages/PySide2/plugins'   ← exists = False
```

于是 Qt 的插件搜索路径是空的，连 `qwindows.dll` 都找不到。你的项目目录叫 **晴雨表**，
所以**任何**放在这个目录下的 Python 环境都会中招。

**修法**（已写进 `main.py`）：在创建 `QApplication` 之前，把真实路径显式写进环境变量：

```python
import PySide2 as _pyside2
_qt_plugins = os.path.join(os.path.dirname(os.path.abspath(_pyside2.__file__)), 'plugins')
if os.path.isdir(_qt_plugins):
    os.environ.setdefault('QT_PLUGIN_PATH', _qt_plugins)
```

Qt 从环境变量读的是原始 Unicode 字符串，绕开了那次有损转换。实测中文目录下已能正常启动，
窗口图标、`cfg.json` 里的 `g` 占位符、两个对话框都正常。

> **一个容易骗到人的细节**：`python -c "import main"` 是**通过**的——
> 导入不需要平台插件，只有真正建 `QApplication` 才炸。
> 所以"导入通过"永远不等于"能启动"。这也是为什么值得把窗口真的构造一遍。
>
> 顺带说明为什么这件事以前没被发现：审计报告附录 B 自己也写了
> "Wetbulb 的 GUI 行为……未在界面上触发"，当时的机器根本跑不起 GUI。

**教训（一句话）**：Windows 上的中文路径是一类独立的失败来源。
项目名、`venv` 路径、exe 所在目录，只要有一处含中文就可能出问题。

### 文献核实那件事的结果（顺带汇报）

你问"依据值是哪篇论文"，我逐条查了一遍，全写进了
[`docs/精度与参考文献.md`](精度与参考文献.md) 和**关于框**（原来是 3 个单行标签、

**顺带更正了三处归属错误**（原来关于框里写的和 README 里暗示的都不准）：

| 原以为 | 实际是 |
|---|---|
| `Wexler-水面` 来自 Wexler (1976) | 两组 Wexler 系数**逐项等于 Hyland & Wexler (1983)**，ASHRAE Trans. 89(2A) |
